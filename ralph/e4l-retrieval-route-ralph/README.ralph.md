## What ralph will build

The Genesis-repo-side slice of master-spec Phase E: a thin, read-only E4L Retrieval Contract
HTTP route deployed alongside the Genesis gateway, plus confirmed dead-code removal and a
doc-drift fix in the same repo.

Chunks (6 total):
- CHUNK_1_CLEANUP: remove the dead `agent_loader.py` 45-slug registry and its `main.py:64-70` import guard (zero successful load path, confirmed by prior audit).
- CHUNK_2_REGISTRY: reconcile the 3 orphaned skill bundles (genesis-domain, genesis-maintenance, genesis-pricing) into the advertised `/agents` catalogue.
- CHUNK_3_DOCS: fix `CLAUDE.md`'s stale "20 agents" claim; document the real 24-bundle / N-of-57-resolvable / unguarded-persona split with a reproducible verification command.
- CHUNK_4_RETRIEVAL: the retrieval route itself — chunk ID format, citation format, superseded filtering, contradiction surfacing, staleness flag, hybrid ranking, refusal path, degraded-connection handling.
- CHUNK_5_TESTS: contract-compliance test suite proving every row of the Retrieval Contract table, without requiring a live assistant-tier Postgres connection.
- CHUNK_6_EVALCLEANUP: delete the stale `evals/` directory (resolved 2026-08-08 — `eval/` is canonical; see `.ralph/guardrails.md`).

## Why 6 chunks, not padded

This workstream's real scope is small on purpose — two independent dead-code/doc-drift fixes
(each genuinely 1-2 hours), one focused feature (a single read-only route against a
not-yet-provisioned external database), and one more dead-code deletion decided after initial
scaffolding (CHUNK_6). Splitting the retrieval work into "route" and "tests" already reflects
this repo's own established convention (the existing Azure/Phoenix ralph workspace at the repo
root does the same route/tests split). Padding further would mean inventing sub-chunks with no
real seam — e.g. splitting the route's ranking logic from its refusal-path logic — that a single
developer would naturally do in one sitting and one PR.

## Prerequisites

- Python 3.12 (`runtime.txt`)
- FastAPI 0.115.6 + uvicorn (`requirements.txt`)
- PostgreSQL client library: psycopg3 (already a repo dependency via `job_store.py`)
- pip (repo uses `requirements.txt`, no poetry/pipenv)
- pytest (not in `requirements.txt` — installed separately, matching the existing root `AGENTS.md`'s own pattern)
- No Docker/Dockerfile in this repo; no container step for local dev

## Setup Before First Run

1. Install dependencies: `pip install -r requirements.txt && pip install pytest`
2. Copy environment file: `cp .env.example .env`
3. Fill in `GATEWAY_API_KEY` (existing) — `ASSISTANT_PG_DATABASE_URL` may stay unset; the route
   is required to degrade gracefully, not require it (see CHUNK_4_RETRIEVAL)
4. No database migration step in this workstream — the assistant-tier PG schema is owned by a
   different, external workstream

## Start ralph

```bash
# Step 1 — Planning mode (run ONCE; produces IMPLEMENTATION_PLAN.md, no code):
cat PROMPT_plan.md | claude

# Step 2 — Verify the plan exists and looks sane:
cat IMPLEMENTATION_PLAN.md

# Step 3 — Build loop (bounded — never run an infinite loop):
bash ~/.claude/skills/ralph-wiggum-loop/scripts/ralph-loop.sh --auto --max-iterations 15
# Windows PowerShell:
#   ~\.claude\skills\ralph-wiggum-loop\scripts\ralph-loop.ps1 -Auto -MaxIterations 15
```

Alternative: run build iterations in-session — invoke the ralph-wiggum-loop skill inside
Claude Code. In that mode Claude acts as ORCHESTRATOR and spawns one fresh subagent per
iteration via the Agent tool (sequentially, one builder at a time) using these same state files.
NEVER run `claude` or the loop scripts through Claude Code's Bash tool — that nests a Claude
session inside a Claude session. The shell scripts above are for an external terminal only.

**Important:** this workspace lives at
`Genesis Agents\ralph\e4l-retrieval-route-ralph\`, but all application code it plans/builds
lands one directory up, at the **repo root** (`Genesis Agents\`) — see PROMPT_build.md. Do not
confuse this with the pre-existing, unrelated ralph workspace already at the repo root
(`Genesis Agents\specs\01_CHUNK_1_DOCKER.md` etc., for the separate Azure/Phoenix migration —
out of scope for this workstream, do not touch).

## When ralph gets stuck

1. Check `.ralph/errors.log` for the failure pattern.
2. Add a guardrail to `.ralph/guardrails.md` so ralph avoids the same pattern.
3. Fix the specific broken file manually if needed (in the repo root, not this workspace).
4. Update `.ralph/state.md` to point at the stuck task.
5. Restart the loop.

## Chunk Completion

When ralph emits `<promise>CHUNK COMPLETE: CHUNK_N_DOMAIN</promise>`:
- Progress is logged automatically.
- ralph moves to the next chunk.
- No manual intervention needed unless you see errors.

## Build Complete

When ralph emits `<promise>BUILD COMPLETE</promise>`:
- All 6 chunks are done and validated.
- Run the full validation gate one more time manually from the repo root:
  `python -m compileall -q main.py retrieval_route.py retrieval_store.py bundle_loader.py && pytest test_retrieval_route.py tests/test_prohibited_tools.py tests/test_escrow_containment.py tests/test_gateway_key_guard.py -q`
- Review `.ralph/progress.md` for the full build history.
